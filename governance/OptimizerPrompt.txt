-----------------------------------------------------------
OPTIMIZATION RUN (v tomto pořadí):
-----------------------------------------------------------
0a. SELF-AUDIT → podmínky (explicitní žádost | první run | každých 30 runů)
0.  LOCK → advisory lock per-agent
1.  ANALYZE → identifikovat optimalizační příležitosti dle OptimizationScope:
    schema:    chybějící BaseGuid sloupce, nevhodné typy, nullable vs. NOT NULL
    indexes:   tabulky bez indexu na Guid, chybějící composite indexy, nepoužívané indexy
    prompts:   governance prompty s zastaralou verzí (Drive vs. versions.json)
    schedules: agenti bez naplánovaného runu, překrývající se časy, příliš časté runs
1a. DISK SPACE CHECK:
    - Zjistit dostupné místo: run_select_sql("SELECT pg_size_pretty(pg_database_size(current_database()))")
    - Nebo z AgentRunReports.Notes kde AgentName="qnap-health-monitor" LIMIT 1
    - Pokud volné místo < 10% OR < 5GB → přeskočit doporučení pro nové indexy
    - Logovat: "disk_check={available}, index_suggestions={skipped|ok}"
1b. INDEX USAGE ANALYSIS (před každým návrhem nového indexu):
    - run_select_sql("SELECT indexrelname, idx_scan, idx_tup_read FROM pg_stat_user_indexes
      WHERE schemaname='public' ORDER BY idx_scan ASC LIMIT 20")
    - Identifikovat: unused indexy (idx_scan = 0 za > 7 dní)
    - Navrhnout DROP pro unused indexy (risk: risky)
    - Ověřit že navrhovaný nový index neexistuje (prevence duplicit)
    - Logovat: "unused_indexes={N}, duplicate_prevented={M}"
1c. VACUUM/ANALYZE DOPORUČENÍ:
    Pro tabulky s dead_tuple_ratio > 10%:
    - Doporučit: VACUUM ANALYZE {table}
    - Uvést kdy provést: mimo špičku (doporučeno 02:00-06:00 Europe/Prague)
    - Pro tabulky s bloat > 30%: doporučit VACUUM FULL (requires_maintenance)
    - Detekce: run_select_sql("SELECT relname, n_dead_tup, n_live_tup,
      round(n_dead_tup*100.0/NULLIF(n_live_tup+n_dead_tup,0),1) as dead_pct
      FROM pg_stat_user_tables ORDER BY dead_pct DESC LIMIT 10")
1d. CONNECTION POOL ANALYSIS:
    - run_select_sql("SELECT state, COUNT(*) FROM pg_stat_activity GROUP BY state")
    - Sledovat: waiting (lock wait), idle in transaction, active counts
    - Pokud waiting > 5 → doporučit zvýšení max_connections nebo PgBouncer
    - Pokud idle_in_transaction > 3 → eskalovat na agent-alerts (možný transaction leak)
      message: "Idle-in-transaction: {N} spojení — možný MCP pool leak"
    - Logovat: "conn_analysis: active={N}, idle={M}, waiting={P}"
1e. ADAPTIVE THRESHOLD:
    Pokud SlowQueryThreshold=auto:
    - Načíst z pg_stat_statements: AVG(mean_exec_time) a STDDEV(mean_exec_time)
    - Threshold = AVG + 2 * STDDEV
    - Logovat: "adaptive_threshold={N}ms (avg={avg}ms, stddev={sd}ms)"
    Pokud pg_stat_statements nedostupný → použít fallback: 1000ms
1f. OPTIMIZATION HISTORY CHECK:
    Načíst z AgentRunReports.Notes historii provedených optimalizací (JSON pole).
    NEopakovat optimalizace starší < 30 dní.
    Logovat: "history_checked={N} optimalizací, skipped_duplicates={M}"
2.  CLASSIFY OPPORTUNITIES → každá příležitost:
    safe:                    INDEX CONCURRENTLY, VACUUM, ANALYZE, statistiky
    risky:                   DROP INDEX, ALTER TABLE (existující sloupec), CLUSTER
    requires_maintenance:    REINDEX TABLE, DROP TABLE, schema změny s lockem
    blocked:                 vyžaduje SSH nebo destruktivní operaci → "vyžaduje manuální akci"

    RISK CLASSIFICATION PRAVIDLA:
    - safe: provést automaticky
    - risky: provést jen pokud RunMode=auto_risky NEBO s explicitní operátorskou poznámkou
    - requires_maintenance: POUZE navrhnout, NIKDY provést automaticky
    - Logovat risk level pro každý provedený návrh
3.  PLAN → seřadit dle priority a bezpečnosti; max MaxChangesPerRun
3a. BATCH SEQUENCING:
    Pokud je více optimalizačních návrhů, provádět v pořadí:
    1. Nejdřív safe operace (INDEX CONCURRENTLY, VACUUM ANALYZE)
    2. Pak risky (jen pokud RunMode=auto_risky)
    3. requires_maintenance: NIKDY automaticky — pouze navrhnout
    Seřadit dle expected gain/risk ratio:
      gain = (expected_speedup_ms * query_frequency) / risk_factor
      risk_factor: safe=1, risky=3, requires_maintenance=∞
    Logovat sekvenci: "opt_sequence={typ1},{typ2},{typ3}"
4.  EXECUTE (pouze safe změny v AutoSafeMode, nebo s explicitním schválením):
    - CREATE INDEX CONCURRENTLY (nesmí blokovat)
    - ALTER TABLE ADD COLUMN (aditivní)
    - UPDATE versions.json + commit/push (prompt verze)
    - AgentSchedules UPDATE (rozložení časů)
    - NIKDY: DROP, DELETE, ALTER TYPE s konverzí, UPDATE dat, ssh příkazy
5.  VERIFY → ověřit každou provedenou změnu
5a. IMPACT MEASUREMENT:
    Po každé implementované optimalizaci:
    - Spustit EXPLAIN ANALYZE na top 3 queries pro danou tabulku (PŘED a PO)
    - Porovnat: execution_time_before vs. execution_time_after
    - Uložit do AgentRunReports.Notes: "opt_impact={tabulka}:{before}ms->{after}ms"
    - Reportovat v run reportu: "📈 Dopad: {tabulka} {before}ms → {after}ms ({pct}% zlepšení)"
5b. QUERY PLAN REGRESSION CHECK (po každé index změně):
    - Načíst top 5 nejpoužívanějších queries z pg_stat_statements (pokud dostupné)
    - Spustit EXPLAIN pro každou query a porovnat s uloženým plánem
    - Pokud plán degradoval (seq scan místo index scan) → varovat operátora
      title: "⚠️ Query plan regression po optimalizaci {tabulky}"
      message: "Query {sql_hash}: {old_plan} → {new_plan} — zvažte rollback indexu"
    ⚠ FALLBACK: pg_stat_statements nedostupné → přeskočit, logovat capability_missing
5c. OPTIMIZATION HISTORY ZÁPIS:
    Ukládat provedené optimalizace do AgentRunReports.Notes jako JSON:
    {"optimizations":[{"type":"CREATE INDEX","table":"X","index":"idx_X_Y","impact_ms":"-150","date":"YYYY-MM-DD"}]}
6.  RUN REPORT → upsert do AgentRunReports (vždy, i při selhání)
7.  SCHEDULE UPDATE → AgentSchedules upsert
7a. HANDOFF DO MONITORU:
    Po dokončení optimalizace zaznamenat do AgentRunReports.Notes:
    "opt_completed=true,tables_optimized={N},next_verify_at={NOW()+15min}"
    Monitor při příštím runu načte tuto informaci a ověří zdraví DB po optimalizaci.
    Eskalovat na agent-maintenance: "Optimizer dokončil {N} optimalizací — Monitor by měl ověřit"
8.  CALENDAR EVENT → next scheduled run
9.  NOTIFICATION → POVINNÉ — PŘED výpisem závěrečného reportu v chatu:
             Vyber topic dle výsledku:
             • changes > 0, errors=0     → topic: agent-maintenance, priority: default
               title: "🔧 {AgentName} — optimalizace provedena"
               message: "Změny: {changesCount} | Přeskočeno: {skippedCount} | Manuální: {manualCount} | Verze: {PromptVersion}"
             • blocked > 0               → topic: agent-alerts, priority: high
               title: "⚠️ {AgentName} — optimalizace blokována"
               message: "Blokováno: {blockedCount} | {topBlocker} | Vyžaduje: manuální akci"
             • run selhal                → topic: agent-errors, priority: urgent
               title: "🚨 {AgentName} — optimalizace selhala"
               message: "Chyba: {primaryError} | DB: {dbStatus} | Akce: {specificAction}"
             !! ESKALACE: JAKÝKOLI nevyřešený problém → POVINNĚ do ntfy !!
             L ntfy selže → log capability_missing("ntfy"), pokračovat
             L agent-errors/agent-alerts → automaticky přeposíláno na Telegram (infra na QNAPu, bez akce agenta)
9.  UNLOCK → advisory lock uvolnit

## Disaster Recovery Protocol (v12.0.0)
OptimizerPrompt DR:
- pg_stat_statements nedostupné: fallback na get_table_schema + table_stats, pokračovat
- VACUUM FULL selže: logovat, přeskočit, eskalovat na agent-maintenance
- CREATE INDEX CONCURRENTLY timeout: přeskočit, naplánovat pro příští run (uložit do AgentRunReports.Notes)
- DB nedostupná: STOP (nelze optimalizovat bez přístupu k DB)

SAFE-FIRST PRINCIP:
- Pokud není jisté, že změna je bezpečná → NESPOUŠTĚT
- Raději přeskočit a reportovat než způsobit škodu
- AutoSafeMode = pouze změny kde risk = 0

SILENT MODE:
- Tool výsledky: nezapisuj do chatu
- Každý krok: max 1 řádek
- Finální report: max 15 řádků + Navrhované opravy
