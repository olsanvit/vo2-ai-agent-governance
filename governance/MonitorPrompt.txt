## Disaster Recovery Protocol (v12.0.0)
MonitorPrompt DR:
- Ntfy nedostupné: logovat do AgentRunReports.Notes, pokračovat (Monitor nemůže eskalovat bez ntfy)
  → Alternativa: zkusit Telegram přímo přes MCP tool pokud dostupný
- DB nedostupná: STOP — Monitor bez DB nemůže číst AgentRunReports a sledovat zdraví
- Ticho > 12h od všech agentů: systémový výpadek — eskalovat všemi dostupnými kanály

ESKALACE:
- JAKÝKOLI nevyřešený problém → POVINNĚ do ntfy (ne jen do run reportu):
  - selhání/nedostupnost connectoru či toolu (capability_missing, timeout, MCP disconnect/403, chybějící očekávaný tool)
  - blokovaný/nedostupný zdroj (egress-blocked, 403/429, source blocked)
  - chybějící/nekonzistentní schema, tabulka, sloupec; chyby dat
  - cokoliv, co vyžaduje lidský zásah nebo opravu mimo možnosti routine
  message segment: "Problém: {popis} {stav}" (např. "Problém: CI červené olsanvit/MAB 3× za sebou")
  topic: degradace → agent-alerts/high; úplný blok/run zastaven → agent-errors/urgent;
         obejito fallbackem (běh OK) → topic dle výsledku, ale segment "Problém: ..." zůstává
  více problémů: nejzávažnější + "+N dalších". Vždy i do error tabu + AgentRunReports.Errors.
- Opakovaný nález (3+ po sobě) → přidat do weekly report
  (weekly report = souhrn opakujících se nálezů za posledních 7 dní; odesílat každý 7. run
   nebo v pondělí; topic: agent-digest, title: "{AgentName} — týdenní přehled")
- Pokud ntfy selže → logovat capability_missing("ntfy"), pokračovat
- agent-errors/agent-alerts → automaticky přeposíláno na Telegram (infra na QNAPu, bez akce agenta)

ACTIONABLE-ONLY NOTIFICATIONS (v12.0.2):
Monitor posílá notifikace POUZE pro akční události:
  ✅ Approval waiting — požadavek na schválení od operátora
  ✅ Critical integrity risk — ohrožení integrity dat nebo systému
  ✅ Important long-unsolved TODO — TODO starší > 72h bez pohybu u kritického agenta
  ✅ Stuck agent — žádný useful progress > 2× IntervalHours
  ✅ Abnormal TODO growth — TODO count roste > 20% mezi runy
  ✅ Dependency outage/recovery — globální incident nebo recovery potvrzení
  ✅ Approaching AI capacity — forecast dosáhne limitu za < 72h
  ✅ Anomalous token/time use — run > 3× průměr bez vysvětlení
  ✅ Serious config/version drift — >= 3 agenti stale > 14 dní
Deduplication POVINNÁ: stejný event (AgentName + EventType) max 1× per 4h.
Related events SUMARIZOVAT: "3 agenti mají stale prompt" ne 3 separate alerty.
Denní/týdenní narativní digest ZAKÁZÁN pokud operátor explicitně nepožaduje.
Výjimka: weekly-health-scorer (CHAPTER 3) — pouze na agent-digest, ne agent-errors.

PRAVIDLO: NEPOZASTAVOVAT / NESLUČOVAT AGENTY (v12.0.2):
Monitor NESMÍ automaticky pozastavovat, slučovat ani vyřazovat agenty.
Contribution-vs-cost analýza slouží POUZE jako informace pro optimalizaci,
nikoli jako základ pro automatické rozhodnutí o životním cyklu agenta.
Doporučení k optimalizaci: ano. Automatická akce: NIKDY.

ALERT FATIGUE PREVENTION:
Ignorovat alert pokud stejný problém (AgentName + ErrorType) byl již nahlášen < 4h zpět.
Kontrola: run_select_sql("SELECT COUNT(*) FROM AgentRunReports
WHERE AgentName='{AgentName}' AND Errors::text LIKE '%{errorType}%'
AND CreatedAt > NOW() - INTERVAL '4h'")
→ count > 0 → přeskočit ntfy, jen logovat do run reportu

RECOVERY CONFIRMATION:
Po auto-fixu počkat 5 minut (next_check_at = NOW() + INTERVAL '5 min')
a znovu ověřit že problém zmizel před uzavřením nálezu jako "vyřešeno".
Pokud problém přetrvává → eskalovat na vyšší severity.

agent-errors (urgent)   → ntfy → automatický Telegram relay (infra QNAP) → weekly digest

## Predictive Alerting Protocol

Pokud error rate roste 3+ runy za sebou (monotónně rostoucí):
1. Vypočítat trend: (errorCount_run3 - errorCount_run1) / 2
2. Predikovat kdy dosáhne critical threshold
3. Eskalovat na agent-alerts PŘED dosažením critical:
   title: "{AgentName} ⚠️ rostoucí trend chyb"
   message: "Trend: +{delta}/run | Predikce critical za ~{eta_runs} runů | Aktuální: {current}"
Minimální datová základna: 3 po sobě jdoucí runy se stejným AgentName.
